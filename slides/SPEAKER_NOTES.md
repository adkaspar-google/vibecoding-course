## Module 03: Directing the Daily Workflow — `Research -> Propose -> Plan -> Implement -> Verify` (`RePPIT`, Slides 10–13)

### Slide 10 — Task Complexity vs. Workflow Rigor & Defeating "Silent Assumption Syndrome"
- **PURPOSE:** Calibrate workflow ceremony to task complexity (Stanford CS146S Lecture 3) and use Socratic Inversion-of-Control (`/grill-me` and Plan Mode) to defeat Silent Assumption Syndrome.
- **VERBAL SCRIPT:** Not every code change needs the same ceremony. Following Stanford CS146S Lecture 3, we match workflow rigor to blast radius: a single-line copy tweak uses a direct prompt; a two-to-four-file bugfix uses a single Plan Mode pass; a medium four-to-twelve-file feature uses the full five-step RePPIT workflow; and a large cross-module refactor uses multi-session stacked subagents. Before planning any non-trivial feature, we must defeat Silent Assumption Syndrome—where RLHF models silently guess auth schemes or retry rules—by inverting control via `/grill-me` or Plan Mode: instructing the agent to interview us about every ambiguity and edge case before writing a single line of code.

### Slide 11 — The 5-Step `RePPIT` Loop (`themodernsoftware.dev` CS146S Lecture 3)
- **PURPOSE:** Detail the 5-step `RePPIT` workflow (`Research -> Propose -> Plan -> Implement -> Verify & Reflect`), highlighting Post-Proposal Context Reset, `Out of Scope` guardrails, and Phase-Based Model Routing.
- **VERBAL SCRIPT:** Slide 11 presents the five-step RePPIT loop from Stanford CS146S. Step 1 is Research: objectively documenting what exists today with exact file-and-line citations while strictly forbidding premature solution proposals. Step 2 is Propose: forcing the agent to generate at least two orthogonal architectural proposals with explicit trade-offs. Here is the critical CS146S rule: once you pick Proposal B, immediately execute a Post-Proposal Context Reset to purge Rejected Proposal A from the context window so unused tokens never confuse implementation! Step 3 is Plan: locking the target files, verification tests, and an explicit Out of Scope, Do Not Touch guardrail list. Step 4 is Implement with Phase-Based Model Routing: using a frontier reasoning model for Research, Propose, and Plan, then routing Implementation to a fast coding model. ## Module 04: Context Window Physics, The 40% "Dumb Zone" & Frequent Intentional Compaction (Slides 14–17)

### Slide 14 — Context Window Physics (`rmvDxxNubIg`): The 40% "Dumb Zone"
- **PURPOSE:** Explain Dex Horthy's stateless `NextAction = LLM(ContextWindow)` law and why reasoning quality degrades past 40% context utilization into the "Dumb Zone".
- **VERBAL SCRIPT:** In his landmark talk No Vibes Allowed, Dex Horthy states the fundamental physical law of coding agents: an LLM is a stateless function where Next Action equals LLM of Context Window. Even if a model advertises a one-million-token window, not all tokens are created equal. From zero to forty percent utilization—the green Smart Zone on our chart—the model maintains sharp attention over every instruction and type invariant. Past forty percent utilization, flooded by unfiltered grep dumps, five-thousand-line test logs, and multi-turn chat arguments, attention diffuses and the agent enters the red Dumb Zone of Context Rot. Optimizing context follows a strict four-part hierarchy: zero incorrect information, zero missing information, minimal noise under forty percent, and a clean forward trajectory.
- **TRANSITION:** How do we prevent verbose tool outputs and tangents from pushing us into the Dumb Zone? Slide 15 covers Context Backpressure and side-queries.

### Slide 15 — Context Backpressure (`karpathy/autoresearch` & `rendergit`) & Side-Queries
- **PURPOSE:** Show how to prevent stdout floods using Karpathy's `autoresearch` shell redirection rule, `rendergit` CXML views, and Claude Code's `/btw` sandboxed side-queries.
- **VERBAL SCRIPT:** Our first defense against the Dumb Zone is Context Backpressure. In `karpathy/autoresearch`, Andrej Karpathy enforces a strict rule: never let a training or test job stream raw output into the agent's context window. Instead, redirect all output to `run.log` and grep only the two metric lines you need—or read the final fifty lines on a crash—compressing fifty thousand log tokens down to forty tokens! Similarly, `karpathy/rendergit` separates a human HTML view from a clean LLM CXML view that strips lockfiles and binary noise. And when you need to ask a quick tangential question mid-session, use Claude Code's `/btw` command so the side-question is answered in a modal and immediately discarded from the transcript.
- **TRANSITION:** What if legitimate multi-file exploration approaches forty percent utilization? Slide 16 introduces Frequent Intentional Compaction and the Human Leverage Pyramid.

### Slide 16 — Frequent Intentional Compaction (FIC), `RPI` & The Human Leverage Pyramid
- **PURPOSE:** Illustrate the Sawtooth Context Utilization pattern via Frequent Intentional Compaction (`research.md` -> `/clear` -> `plan.md` -> `/clear`) and the Human Attention Leverage Pyramid.
- **VERBAL SCRIPT:** Look at the left chart on Slide 16. While a naive chat session accumulates tokens monotonically into the red Dumb Zone, Frequent Intentional Compaction creates a green sawtooth curve that stays below forty percent across the entire feature lifecycle. ## Module 06: Harness Engineering Layer 2 — Progressive-Disclosure Skills (`agentskills.io`), Curated Grounding (`context-hub`), Ergonomic MCP & Meta-MCP "Code Mode" (Slides 22–26)

### Slide 22 — Skills as On-Demand Procedural Manuals (`agentskills.io`)
- **PURPOSE:** Explain the `agentskills.io` 3-Level Progressive Disclosure architecture and the 3-Stage Skill Maturity Lifecycle.
- **VERBAL SCRIPT:** Skills are on-demand procedural manuals governed by the open `agentskills.io` standard. To scale to dozens of workflows without bloating startup context, skills use three-level progressive disclosure. At Level 1, only the YAML frontmatter `name` and `description`—about one hundred tokens per skill, stating both positive `Use when` triggers and negative `Don't use for` boundaries—load at session startup. At Level 2, when triggered, the agent reads the `SKILL.md` body of up to 500 lines containing exact CLI recipes and experience-grounded gotchas. At Level 3, bundled `scripts/`, `references/`, and `assets/` cost zero tokens until selectively executed or read. Across the three-stage maturity lifecycle, skills graduate from personal prototype to team preview to eval-gated production GA—and are retired when newer model weights absorb the capability natively.
- **TRANSITION:** How can a skill eliminate stale-SDK hallucinations and get smarter every time an agent runs? Slide 23 examines Andrew Ng's `context-hub`.

### Slide 23 — Curated API Grounding & Self-Improving Annotations (`andrewyng/context-hub`)
- **PURPOSE:** Detail how `andrewyng/context-hub` (`@aisuite/chub` and `get-api-docs/SKILL.md`) provides curated versioned API docs and local self-improving session annotations (`chub annotate`).
- **VERBAL SCRIPT:** Pretrained models frequently hallucinate deprecated SDK methods or outdated webhook signatures, while raw web searches pull noisy HTML. Andrew Ng's `context-hub`—the `chub` CLI paired with `get-api-docs/SKILL.md`—solves this through a four-stage self-improving loop. First, instead of guessing an API, the agent triggers the skill and runs `chub search` and `chub get stripe/api --lang py` to fetch clean, version-pinned Markdown documentation on demand. Second, when the agent discovers a non-obvious runtime quirk during testing—like requiring raw bytes for HMAC verification—it runs `chub annotate` to persist a local note. Future sessions automatically load that note via `--with-annotations` inside guarded untrusted-input tags, and send quality signals upstream via `chub feedback`.
- **TRANSITION:** Just as progressive disclosure keeps skills lean, how do we stop MCP servers from flooding context? Slide 24 presents Ergonomic MCP Design and Meta-MCP Code Mode.

### Slide 24 — Ergonomic MCP Tool Design & Meta-MCP "Code Mode" (>90% Token Savings)
- **PURPOSE:** Present Stanford CS146S Lecture 4's 4 Rules of Ergonomic Agent Tools and the token bar chart comparing 150 CRUD MCP tools against Meta-MCP `search` + `execute` "Code Mode".
- **VERBAL SCRIPT:** Why do naive one-to-one wrappers around REST APIs fail as MCP tools? Because low-level CRUD endpoints force the LLM to make multiple sequential round-trips while dumping forty-eight thousand tokens of JSON schemas into the window! Stanford CS146S Lecture 4 establishes four rules for ergonomic agent tools: first, design around high-level outcomes rather than granular CRUD; second, enforce strict Pydantic or TypeScript schemas instead of untyped dicts; third, return actionable self-repairing error messages; and fourth, adopt Meta-MCP Code Mode. Instead of exposing 150 tool schemas upfront, Code Mode exposes just two meta-tools: `search` to query relevant tool schemas on demand, and `execute` to run a generated Python or TypeScript script inside a sandbox VM—slashing tool token consumption by over ninety-five percent!

- **PURPOSE:** Explain Karpathy's 3-stage `llm-council` protocol and compare `git worktree` (Provisioning Cost) against colocated Jujutsu (`jj`, Integration Cost) for parallel AI coding agents (`wavect.io` & `jj-vcs/jj`).

### Slide 32 — Remediation-Aware Architectural Linters (OpenAI Harness Engineering)
- **PURPOSE:** Contrast cryptic human linter messages against OpenAI's `[VIOLATION] -> [WHY] -> [HOW TO FIX]` remediation-aware linter pattern.
- **VERBAL SCRIPT:** Traditional linters were written for human engineers who already know the codebase architecture. When a standard linter tells an agent `E901 Forbidden import db.session`, the agent doesn't know what to call instead—so it wastes four turns grepping around or slaps a `# noqa` comment on the line to silence the error! OpenAI's Harness Engineering team solved this by writing custom structural linters whose error messages are structured as three-part remediation recipes for the LLM: first, `[VIOLATION]` stating the exact layer rule broken; second, `[WHY]` explaining the architectural invariant; and third, `[HOW TO FIX]` giving the exact replacement import and dependency-injection pattern. This turns multi-turn debugging into single-turn autonomous self-repair.
